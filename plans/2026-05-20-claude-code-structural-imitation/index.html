    Research: imitate Claude Code structural patterns in KARIANA#

    Status: experimental research branch feat/claude-code-structural-imitation. Not for production. Not for TVN. This branch exists to evaluate whether porting the structural decomposition popularised by Claude Code (via the public Rust imitator ultraworkers/claw-code) improves KARIANA's effectiveness — response accuracy, log clarity, and overall polish over the current v0.11.3 dev state.

    Research question#

    Claude Code's structure — readable through the open-source claw-code Rust port — is a 9-crate decomposition with explicit boundaries between provider/runtime/tools/ permissions/telemetry/test-doubles. KARIANA's stack is C++ (UE plugin) + Python (daemon backend) and cannot be ported wholesale. Can we adopt the structural patterns while keeping the C++/Python stack, and does doing so measurably improve KARIANA?

    Success criteria for the experiment:

    1. Response accuracy: mock-parity harness catches at least one regression class that current unit tests miss (e.g. tool counter desync, premature "finished", poisoned-session-on-502).
    2. Log clarity: a single structured event stream replaces ad-hoc UE_LOG / Python logging calls scattered across the bridge and backend.
    3. Polish: UI counters and labels derive from event stream rather than mutated local state; session lifecycle has explicit operations rather than implicit "talk to the daemon and hope".

    Non-goals#

    • Not for TVN re-demo (2026-06-02). TVN uses KARIANA-tvn fork. Nothing here ships to TVN.
    • No version bump, no release, no installer rebuild. Step 8/9 of the standard dev workflow are explicitly skipped for this branch.
    • No rewrite to Rust. UE plugin stays C++; daemon stays Python. We are imitating the structure not the language.
    • No upstream merge until the experiment is judged. Branch stays open as a draft PR for review/discussion.

    The 7 structural lessons#

    Each lesson below lists:

    • Current KARIANA state (file paths, LOC at branch base 0867adcc)
    • claw-code reference (the file or crate to study)
    • Target KARIANA state (concrete files to add or modify)
    • Acceptance criteria (how we know the lesson landed)
    • Risk (low / medium / high — drives ordering)

    Lesson 6 — Mock parity harness ⭐ highest leverage#

    Implemented first because it is purely additive (test-only), demonstrates the imitation pattern most clearly, and unlocks regression detection for every other lesson.

    • Current: Content/Python/tests/{test_bedrock_backend.py, test_deterministic_mcp.py, test_mode_tool_gating_repro.py} — unit-level only. No deterministic mock backend; tests either stub or hit live services.
    • Reference: rust/crates/mock-anthropic-service/ + rust/crates/rusty-claude-cli/tests/mock_parity_harness.rs + rust/mock_parity_scenarios.json (12 scenarios, 21 captured /v1/messages requests).
    • Target:
    • Content/Python/tests/parity/server.py — fake Bedrock + LM Studio HTTP server replaying captured JSON responses.
    • Content/Python/tests/parity/scenarios/*.json — seed with 3:
      • streaming_text.json — basic streaming reply
      • multi_tool_turn.json — assistant invokes 2+ tools in one turn
      • error_502_session_reset.json — backend returns 502 mid-turn; harness asserts session is reset, not poisoned
    • Content/Python/tests/parity/runner.py — pytest-discoverable; loads scenario, points the backend at the fake server, captures actual transcript, diffs against expected.
    • scripts/run_parity_diff.py — CLI wrapper for local invocation outside pytest.
    • Acceptance: pytest Content/Python/tests/parity/ green; intentionally injecting the PR #615 bug (no history reset on 502) makes error_502_session_reset.json fail.
    • Risk: Low (test-only, no production code touched).

    Lesson 2 — Session lifecycle as first-class operations#

    • Current: KarianaChatSession.cpp (529 LOC) + KarianaSessionController.cpp (568 LOC) hold the type; daemon (bedrock_backend.py:1661 LOC) owns history. No explicit Reset() or Compact() API. C++ only holds SessionId. Symptom: PR #615 (502 errors poison the session because there is no reset hook).
    • Reference: rust/crates/runtime/src/{session.rs, session_control.rs, conversation.rs, compact.rs, summary_compression.rs} — five files, one concern.
    • Target:
    • KarianaChatSession::Reset() — wipes daemon-side history for the session ID and resets local UI state.
    • KarianaChatSession::Compact() — triggers daemon-side summary compression, returns the new compacted state.
    • bedrock_backend.py exposes reset_session(session_id) and compact_session(session_id) RPC handlers.
    • Backend automatically calls reset_session from its 502 error path before bubbling the error to C++ (closes the PR #615 bug class).
    • Acceptance: error_502_session_reset.json parity scenario passes. Manual UE test: trigger a 502, observe the session is usable on retry.
    • Risk: Low-Medium (adds new methods; existing call sites unchanged).

    Lesson 7 — Telemetry as a separate layer#

    • Current: Content/Python/backends/events.py (47 LOC) — seed exists but underused. Logging sprinkled across bridge + backend + handlers via UE_LOG / logging.getLogger. UI tool-call counter is mutated local state (PR #601 bug class).
    • Reference: rust/crates/telemetry/ — separate crate, one job.
    • Target:
    • Content/Python/telemetry/__init__.py — promote from single file.
    • Content/Python/telemetry/events.py — structured event types: ToolCallStarted, ToolCallCompleted, MessageReceived, MessageStreamChunk, BackendError, SessionReset, SessionCompacted.
    • Content/Python/telemetry/emitter.py — single emit(event) function backends call instead of logging.info.
    • Content/Python/telemetry/sink_log.py — default sink writes to existing log channels.
    • Content/Python/telemetry/sink_ipc.py — sink that ships events over the existing daemon→C++ pipe so the UI can consume them.
    • C++ side: a KarianaTelemetryStream subscriber that the chat panel reads from for counters / labels.
    • Acceptance: Tool-call counter reads from event count, not local mutation. Killing the daemon mid-turn produces a BackendError event the UI surfaces. Parity harness can assert on event sequences.
    • Risk: Medium (touches UI binding for counter — needs careful migration).

    Lesson 4 — Permission as a layer, with hooks as the extension point#

    • Current: KarianaApprovalController.cpp (145 LOC) exists but is too thin to gate 40 handler files. Permission decisions scattered. No hooks extension point for users.
    • Reference: rust/crates/runtime/src/{permission_enforcer.rs, hooks.rs, policy_engine.rs, trust_resolver.rs}.
    • Target:
    • Content/Python/backends/permissions_map.py — declarative {handler_name: PermissionLevel} map. Levels: auto_allow / prompt_once / prompt_each / deny.
    • Content/Python/backends/hooks.py — PreToolUse, PostToolUse, Stop hook dispatch. Default no-ops. User overrides via project-level .kariana/hooks.py.
    • KarianaApprovalController grows to consume the map (RPC fetches it from daemon at session start).
    • Acceptance: Adding a tool to permissions_map.py with deny causes KarianaApprovalController to reject it without code changes elsewhere. A user-provided PreToolUse hook can veto a tool call.
    • Risk: Medium (changes approval flow — must preserve existing UX for already-approved tools).

    Lesson 3 — Tool validation as separate submodules#

    • Current: 40 handler files, no validation layer. python_execution_commands.py and python_commands.py run user-provided Python with minimal guards. No symlink/path/binary-detection guards on file writes.
    • Reference: rust/crates/runtime/src/bash_validation.rs — 6 submodules: readOnlyValidation, destructiveCommandWarning, modeValidation, sedValidation, pathValidation, commandSemantics.
    • Target:
    • Content/Python/backends/validators/__init__.py
    • Content/Python/backends/validators/python_exec.py — read-only mode check, dangerous import allowlist, exec timeout enforcement.
    • Content/Python/backends/validators/file_path.py — workspace-boundary check, symlink-escape guard, path traversal.
    • Content/Python/backends/validators/file_content.py — binary detection, size limit.
    • tool_executor.py calls validators before dispatch.
    • Acceptance: Symlink-escape attempt fails with a clear error. Writing a 500 MB file is rejected pre-flight. Parity scenario validator_blocks_symlink_escape.json passes.
    • Risk: Medium (must preserve existing successful tool calls — false-positive risk).

    Lesson 5 — MCP lifecycle hardening as a named module#

    • Current: MCP code exists across Source/UnrealMCPBridge/ + Source/GenerativeAISupportEditor/Private/MCP/. Retry/timeout/dead-server-detection logic is scattered.
    • Reference: rust/crates/runtime/src/mcp_lifecycle_hardened.rs — one file, one job: edge cases.
    • Target:
    • Source/UnrealMCPBridge/Private/MCPLifecycleHardening.cpp + .h — collects connection retries, exponential backoff, dead-server probes, malformed-message handling, graceful shutdown.
    • Existing MCP files delegate to it instead of inlining hardening.
    • Acceptance: Killing the MCP server mid-call surfaces a clean error within 5 seconds (not a hang). Restarting it auto-reconnects.
    • Risk: Medium (extraction risk — easy to miss a code path).

    Lesson 1 — Split god-objects (deferred, highest risk)#

    Done last, after the additive lessons are stable, so the splits land on top of a more disciplined surface.

    • Current:
    • KarianaClaudeCodeBridge.cpp — 1331 LOC
    • bedrock_backend.py — 1661 LOC
    • tool_schema.py — 1749 LOC
    • Reference: rust/crates/runtime/src/ — ~25 single-purpose files, mostly ≤400 LOC each.
    • Target: each file split into ≤400-LOC single-purpose siblings matching the responsibilities exposed by lessons 2/4/7 above. Exact split TBD after the additive work.
    • Acceptance: no file in the touched set exceeds 400 LOC. All tests (existing unit + new parity) still green.
    • Risk: High. Mechanical but invasive. Done in its own PR, separately reviewed.

    Sequencing in this branch#

    Order Lesson Why this slot
    1 6 — Mock parity harness Pure additive; unlocks regression detection for everything else
    2 2 — Session lifecycle methods Small, surgical; fixes PR #615 bug class; parity scenario already drafted in lesson 6
    3 7 — Telemetry layer Additive; enables event-driven UI binding for lesson 4
    4 4 — Hooks + permission map Builds on telemetry events
    5 3 — Validators Additive; benefits from telemetry to surface rejections
    6 5 — MCP lifecycle hardening Extraction; cleaner after telemetry exists
    7 1 — Split god-objects Last; built on stable additive surface

    Open decisions#

    1. Should permissions_map.py ship a default that matches today's effective policy (no behaviour change), or default to stricter rules? Default: match today, change later.
    2. Telemetry events over the existing daemon pipe vs. a separate channel? Default: existing pipe with a tag prefix, to avoid pipe-multiplication.
    3. Does the Compact() operation use the local LLM (LM Studio) when available? Default: yes, falls back to Bedrock if not.
    4. Validators block by raising, or by emitting a BackendError event and returning a tool-error? Default: tool-error event, so the LLM can recover.

    Acceptance criteria for the whole experiment#

    The branch is judged successful if:

    • All 7 lessons land as described, with green tests.
    • The mock parity harness (lesson 6) is adopted as part of the regular dev cycle.
    • At least one historical bug class (PR #601 tool counter, PR #615 session poison) is provably blocked by the new structure in the harness.
    • A team member who didn't write the branch can read this doc and the resulting files and explain how a message becomes a tool call.

    If those criteria fail, the branch is closed and the lessons are documented as "tried, didn't help" in docs/decisions/.
