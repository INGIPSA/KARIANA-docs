    TL;DR#

    The C++ reflection toolset port from UE 5.8's ToolsetRegistry is fully working in UE 5.7. The demo UKarianaBlueprintToolset.CreateBlueprint and .CompileBlueprint are reachable over port 9877 from any MCP client; a real UBlueprint asset gets authored end-to-end through the reflection layer with zero hand-written schema.     Time path of a successful KarianaBlueprintToolset.CreateBlueprint call:

    1. MCP client sends {"type":"KarianaBlueprintToolset.CreateBlueprint","params":{...}} to 127.0.0.1:9877
    2. Content/Python/unreal_socket_server.py:_try_cpp_registry (extended in §3 below) sees the . in the type, asks unreal.get_editor_subsystem(unreal.KarianaToolsetSubsystem) whether the toolset exists, and if so calls subsys.execute_tool_blocking(...)
    3. C++ UKarianaToolsetSubsystem::ExecuteToolBlocking waits on the future from ExecuteTool, which delegates to Kariana::Reflection::FFunctionLibraryToolset::ExecuteToolInternal
    4. That looks up the FObjectFunctionToolCall, packs JSON params into the function's frame memory via KarianaToolsetJson::JsonDataToStruct, sets up an FFrame, and calls UFunction::Invoke
    5. UKarianaBlueprintToolset::CreateBlueprint runs as ordinary editor C++, creates the package, calls FKismetEditorUtilities::CreateBlueprint(ParentClass, Package, Name, BPTYPE_Normal, UBlueprint::StaticClass(), UBlueprintGeneratedClass::StaticClass())
    6. Return value is read out of the frame memory via KarianaToolsetJson::PropertyToJsonData, wrapped in {"returnValue": ...}, and shipped back through the same chain in reverse

    2. What did NOT initially work — and how it was fixed#

    2.1 Symptom#

    $ python scripts/_probe_kariana_reflection_toolset.py
[1/3] tools/list ...
     payload: 57 bytes
     0 tools surfaced
     FAIL — no KarianaBlueprintToolset.* tools found
     names seen: []

    Direct socket inspection:

    >>> # send {"command": "tools/list"} on port 9877
>>> response
{"success": false, "error": "Unknown command type: None"}

    2.2 Root cause#

    There are two socket servers in this codebase, listening on different ports:

    Listener Implemented in Port Used by
    C++ FMCPSocketServer Source/UnrealMCPBridge/Private/MCPSocketServer.cpp:17 (Port(9000)) 9000 Currently nothing routes here; appears to be dormant
    Python unreal_socket_server.py Content/Python/unreal_socket_server.py 9877 All MCP clients (Claude Code, kariana-remote, Bedrock daemon, etc.)

    When I wired the reflection bridge into FPythonBridge::PreDispatchHook, I assumed FPythonBridge::ExecuteCommand was the entry point for port-9877 traffic. It is not. The Python socket server reads requests directly and dispatches via its own _try_cpp_registry path (unreal_socket_server.py:503), which calls unreal.KarianaCommandRegistryBPLib.has_command(...) — a separate C++ registry from our reflection toolsets.

    Additionally:

    • The Python socket server reads command["type"], not command["command"]. The _probe_kariana_reflection_toolset.py probe used command and got "Unknown command type: None".
    • No code path on port 9877 ever calls FPythonBridge::ExecuteCommand for ordinary tool dispatch.

    3. The gap is small — closing path#

    Two changes, both ~10 lines:

    3.1 Expose UKarianaToolsetSubsystem to Python via UFUNCTION#

    Source/KarianaToolsetBridge/Public/Reflection/KarianaToolsetSubsystem.h — add UFUNCTION(BlueprintCallable) to two methods:

    UFUNCTION(BlueprintCallable, Category="Kariana|Reflection")
FString GetToolsListJson() const;

UFUNCTION(BlueprintCallable, Category="Kariana|Reflection")
FString ExecuteToolBlocking(const FString& QualifiedToolName, const FString& JsonInput);

    ExecuteToolBlocking is a thin sync wrapper around the existing ExecuteTool(...) future — Python doesn't need futures.

    3.2 Extend Python dispatcher#

    Content/Python/unreal_socket_server.py:503 — the existing _try_cpp_registry already probes unreal.KarianaCommandRegistryBPLib. Add a second probe for the reflection toolset:

    def _try_cpp_registry(self, command_type, command):
    # Existing path: KarianaCommandRegistryBPLib...
    if unreal.KarianaCommandRegistryBPLib.has_command(command_type):
        ...
        return cpp_result

    # NEW: reflection toolset probe (matches "<Toolset>.<tool>")
    if "." in command_type:
        subsys = unreal.get_editor_subsystem(unreal.KarianaToolsetSubsystem)
        if subsys:
            params_json = json.dumps(command.get("params", {}))
            result_json = subsys.execute_tool_blocking(command_type, params_json)
            if result_json:
                return json.loads(result_json)
    return None

    3.3 Update _probe_kariana_reflection_toolset.py#

    Send {"type": tool_name, ...} instead of {"command": ..., ...}. Already mismatched today regardless of the bridge.

    Total estimate: ~30 min of work + one rebuild + one editor restart.

    7. Recommendation#

    Port complete. The §3 Python integration landed and the smoke probe passes all three checks (see §1.4 for the live trace). Next decisions:

    1. Which existing tools to migrate first. Strongest candidates: blueprint authoring (create_blueprint, add_node_to_blueprint, connect_blueprint_nodes, compile_blueprint), UMG widget creation, PCG graph editing — anywhere the hand-authored Python schema dict is large or where return shapes are USTRUCTs.
    2. Whether to broaden UKarianaBlueprintToolset. The current demo exposes only CreateBlueprint + CompileBlueprint. Adding AddNode, ConnectPins, AddVariable would put the schema-quality benefit in front of the same workflows BlueprintLisp targets.
    3. Async return support. Currently dropped from the v1 port (sync only). Add when an async tool actually needs it; the rewiring is local to KarianaObjectFunctionToolCall::Execute and UKarianaToolsetSubsystem::ExecuteToolBlocking.
    4. Deprecate the dead FPythonBridge::PreDispatchHook. It's installed but never fires — port 9877 traffic doesn't pass through C++ ExecuteCommand. Either repurpose it for the C++ FMCPSocketServer (port 9000) when that listener is brought back, or remove it. Low priority.

    Time spent on this work: roughly one focused session including the planning, comparison report, port plan, vendoring + KARIANA-original substitutes for the 5.7 gaps, fixing two real bugs (load-order, fast-path inversion) caught only at runtime, and the Python integration. The 5.7-vs-5.8 API delta findings are saved as project memory for the next time someone backports an experimental Epic plugin.
