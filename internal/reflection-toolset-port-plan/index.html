    Reflection-Driven Toolset Port — UE 5.8 → KARIANA on UE 5.7#

    Status: Phases 1–3 complete; build green against UE 5.7 on 2026-05-10. Live editor smoke test pending (user-initiated). Goal: Bring Epic's reflection-driven AI toolset infrastructure (the engine that powers UToolsetDefinition + UFUNCTION(meta=(AICallable))) into KARIANA on UE 5.7, so future MCP tools can be authored as plain C++ static functions instead of hand-written Python schema dicts.

    This plan supersedes the v0.1 dispatch shim in Source/KarianaToolsetBridge/ and the speculative design in toolset-registry-interop-design.md. The earlier comparison report (epic-mcp-comparison.md) remains accurate as background.

    1. Why this is the right backport#

    The 5.8 Toolsets/ plugins (UMGToolSet, GASToolsets, PCGToolset, etc.) all share a single pattern:

    UCLASS(BlueprintType)
class UUMGToolSet : public UToolsetDefinition
{
    GENERATED_BODY()
public:
    UFUNCTION(meta = (AICallable), Category = "UMG|Creation")
    static UWidgetBlueprint* CreateWidgetBlueprint(
        const FString& FolderPath,
        const FString& AssetName,
        TSubclassOf<UUserWidget> ParentClass,
        TSubclassOf<UWidget> RootWidgetClass = nullptr);
    // ...
};

    That's it. No JSON schema authored by hand. FFunctionLibraryToolset reflects over the UClass at registration time, generates the MCP tools/list schema from FProperty metadata, and dispatches tools/call through FFrame/UFunction::Invoke. Every body is plain editor C++ (FKismetEditorUtilities::CreateBlueprint, UWidgetBlueprint, etc.) that already exists in 5.7.

    KARIANA today has 200+ Python handler files where each tool has a hand-written schema dict. Porting the reflection layer lets us migrate hot tools (especially blueprint authoring, where schemas are large and fiddly) to C++ at our own pace.

    3. Subsystem & socket integration#

    5.8 ships a UToolsetRegistrySubsystem (UEditorSubsystem) that holds an FToolsetRegistry instance and exposes a TValueOrError<TObjectPtr<UToolsetRegistrySubsystem>, FString> Get() accessor. We mirror this:

    UCLASS()
class UKarianaToolsetSubsystem : public UEditorSubsystem
{
    Kariana::Reflection::FToolsetRegistry ToolsetRegistry;
public:
    static UKarianaToolsetSubsystem* Get();
};

    FUnrealMCPBridge (Source/UnrealMCPBridge/Private/) is KARIANA's TCP socket server on port 9877. Today it dispatches to Python handlers. We add a thin C++ pre-dispatch step:

    On incoming command:
  1. If type == "tools/list":
       merge subsystem->ToolsetRegistry.GetToolsetJsonSchemas()
       with python_tool_schemas() → respond
  2. If type == "tools/call" and name starts with a registered toolset prefix:
       dispatch to subsystem->ToolsetRegistry.ExecuteTool()
       → return future result
  3. Else: existing Python dispatch path (unchanged)

    Backwards-compatible: Python clients see a richer tools/list and can call C++ tools by name, but every existing tool keeps working.

    4. Demo: UKarianaBlueprintToolset#

    Phase-3 deliverable. A single UCLASS exposing 3–4 functions that today require multiple Python tool calls:

    UCLASS()
class UKarianaBlueprintToolset : public UKarianaToolsetDefinition
{
    GENERATED_BODY()
public:
    UFUNCTION(meta = (AICallable, AIDescription="Create a new Blueprint asset and return the asset path."))
    static FSoftObjectPath CreateBlueprint(
        const FString& FolderPath,
        const FString& AssetName,
        TSubclassOf<UObject> ParentClass);

    UFUNCTION(meta = (AICallable))
    static bool CompileBlueprint(UBlueprint* Blueprint);

    UFUNCTION(meta = (AICallable))
    static bool AddVariableToBlueprint(UBlueprint* Blueprint, FName VarName, FEdGraphPinType PinType);
};

    Implementation reuses FKismetEditorUtilities::CreateBlueprint exactly as 5.8's UMG toolset does (verified at E:\ue5.8-dev\...\UMGToolSet.cpp:194). Existing KARIANA Python create_blueprint handler stays in place; this is an additional, faster, schema-better path.

    5. Risks tracked#

    ID Risk Mitigation
    P-1 UE 5.7 lacks some TStrongObjectPtr / TWeakObjectPtr::Pin() ergonomics used by FFunctionLibraryToolset. Verified TWeakObjectPtr::Pin() exists in 5.7 since 5.0. If a specific overload is missing, replace with TWeakObjectPtr::Get() + nullptr check.
    P-2 meta=(AICallable) is a project-defined metadata key. UHT in 5.7 may emit a warning about unknown meta. Add it to Build.cs MetaDataKeysAllowed or live with the warning — it's non-fatal.
    P-3 UFunction::Invoke script execution requires a CDO instance for static functions. 5.8 uses GetMutableDefault<UToolsetDefinition>() — port verbatim.
    P-4 Output USTRUCTs serialize via the registered FToolsetJsonConverter chain — we're skipping converters in Phase 1. Phase 1 exposes only primitive returns + FString/FName. UStruct returns flagged for Phase 4.
    P-5 KARIANA ships closed-source; vendoring Epic's MIT-licensed engine sources is fine but each file needs the Epic copyright preserved. Keep // Copyright Epic Games, Inc. All Rights Reserved. header on every vendored file. Add a NOTICES line in KARIANA.uplugin.

    6a. Substitutions made for 5.7 compatibility#

    5.8 facility KARIANA replacement Reason
    JsonUtilitiesEditor module + FJsonSchemaGenerator (1,492 LOC engine code) KarianaToolsetJson.{h,cpp} (~400 LOC, KARIANA-original) Whole subsystem is 5.8-only. We hand-rolled enough reflection-to-JSON-Schema for common UFUNCTION shapes.
    FScopedScriptExceptionHandler (thread-local script error handler) Global FBlueprintCoreDelegates::OnScriptException only 5.7 only ships the global multicast. Functional regression: errors raised on non-game-thread tools won't be captured (acceptable — tools run on game thread).
    UKismetSystemLibrary::RaiseScriptError (declared but not exported in 5.7) Kariana::Reflection::RaiseToolScriptError 5.7 omits ENGINE_API decorator on the engine version, so the symbol can't be linked from another module. We replicate the function locally using FBlueprintCoreDelegates::ThrowScriptException directly.
    UToolCallAsyncResult + FutureHandler async return path Dropped from v1 — all returns are sync Simplification. KARIANA tools are sync today. Re-add when an async tool lands.
    Custom FToolsetJsonConverter chain for type-overrides (FToolsetReference, etc.) Not yet ported Phase 4 if needed. The current schema treats UObject* / UClass* as path strings.
