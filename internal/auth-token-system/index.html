    Authentication Token System#

    Offline-capable license verification for the KARIANA UE plugin. Users authenticate once online via Clerk, receive a signed token cached locally, then work offline for up to 30 days.

    Architecture#

    ┌─────────────┐     ┌──────────────┐     ┌────────────────────────┐
│ UE Plugin   │     │ K9 Daemon    │     │ Clerk (cloud)          │
│             │     │              │     │                        │
│ Auth check  │◄────│ Token file   │◄────│ OAuth callback         │
│ on startup  │     │ generation   │     │ (user_id, tier, email) │
└─────────────┘     └──────────────┘     └────────────────────────┘

    Flow#

    1. Plugin starts → UKarianaAuthToken::LoadAndVerify() reads %LOCALAPPDATA%/KARiANA/.kariana_token
    2. No token → Auth screen shows "Login to Kariana" + "Setup Local Model" pills
    3. Expired token → Auth screen shows "Your subscription seems expired!" + "Login to Kariana"
    4. Invalid/tampered token → Same as no token (auth screen)
    5. Valid token → Welcome screen with quick-action cards (normal plugin use)

    Login flow#

    1. User clicks "Login to Kariana" → browser opens https://app.kariana.ai/sign-in
    2. User authenticates via Clerk (Google or Email)
    3. Clerk callback reaches the K9 daemon with user claims (user_id, email, tier)
    4. Daemon calls token_generator.generate_token() → signs payload with HMAC-SHA256
    5. Daemon saves signed token to %LOCALAPPDATA%/KARiANA/.kariana_token
    6. Plugin polls for the token file every 2 seconds → detects it → switches to welcome screen

    Setup Local Model flow#

    1. User clicks "Setup Local Model"
    2. If no token exists (never authenticated) → error: "You need internet connection for the first time"
    3. If token exists (even expired) → opens plugin Project Settings + local model docs

    Token Format#

    The token is a JSON file with two fields: a payload and an HMAC-SHA256 signature.

    {
  "payload": {
    "user_id": "clerk_user_abc123",
    "email": "user@example.com",
    "tier": "solo",
    "issued_at": "2026-03-26T12:00:00Z",
    "expires_at": "2026-04-25T12:00:00Z"
  },
  "signature": "91368c674df621aec225949b0adf31875ed68dd12317995b529f81f1d0018a2d"
}

    Payload fields#

    Field Type Description
    user_id string Clerk user ID
    email string User email
    tier string "free", "solo", "pro", "enterprise"
    issued_at ISO 8601 When the token was generated
    expires_at ISO 8601 When the token expires (default: 30 days)

    Signature#

    • Algorithm: HMAC-SHA256
    • Input: canonical JSON of the payload (compact, sorted keys, no whitespace)
    • Output: lowercase hex string (64 chars)
    • The signing key is shared between the server (Python) and the plugin (C++, obfuscated with XOR)

    File Locations#

    Token file (per-user, runtime)#

    Platform Path
    Windows %LOCALAPPDATA%\KARiANA\.kariana_token
    macOS ~/Library/Application Support/KARiANA/.kariana_token
    Linux ~/.config/KARiANA/.kariana_token

    Subscription Tiers#

    Defined in EKarianaSubscriptionTier (C++) and cloud/clerk/types.ts:

    Tier Clerk Value Description
    None — No token / invalid
    Free "free" Free tier (future)
    Solo "solo" Solo subscription (active for pre-release)
    Pro "pro" Pro tier (future)
    Enterprise "enterprise" Enterprise (contact sales)

    Auth States#

    Defined in EKarianaAuthState:

    State Meaning UI Shown
    NoToken No .kariana_token file on disk First-time auth pills
    Valid Token exists, signature valid, not expired Welcome screen / chat
    Expired Token exists, signature valid, but past expires_at "Subscription expired!"
    Invalid Token file exists but signature verification failed First-time auth pills

    Security Notes#

    • The token is signed, not encrypted — users can read their tier, but cannot change it without invalidating the signature
    • The signing key is obfuscated in the plugin binary (XOR with a mask) — not true encryption, but sufficient to prevent casual tampering
    • Before shipping to production, replace the placeholder signing key in both:
    • KarianaAuthToken.cpp — OBFUSCATED_KEY[] array (XOR each byte of your real key with 0xA7)
    • token_generator.py — _DEFAULT_KEY (or set KARIANA_TOKEN_SIGNING_KEY env var on the server)
    • Constant-time comparison is used for signature verification to prevent timing attacks
    • Token expiry is checked against FDateTime::UtcNow() — clock manipulation is a known limitation (acceptable for this use case)

    Testing#

    Python tests (run locally)#

    cd Content/Python
python -m pytest licensing/test_token_generator.py -v

    Covers: generation, verification, tampering rejection, expiry, key management, canonical JSON determinism.

    Manual token generation#

    cd Content/Python
python -m licensing.token_generator --user-id test_001 --email test@kariana.ai --tier solo --days 30 --save

    Daemon integration#

    Send to the daemon via stdin JSON-line:

    {"cmd": "auth_callback", "user_id": "clerk_user_abc123", "email": "user@kariana.ai", "tier": "solo"}

    The daemon responds with:

    {"type": "auth_success", "user_id": "clerk_user_abc123", "tier": "solo", "token_path": "C:\\Users\\...\\KARiANA\\.kariana_token"}
